# Протокол задач для Grok Build

Ветка `build-inbox` — канал задач между ботом-менеджером проекта и Grok Build (CLI на Windows-компьютере владельца; вотчер Build периодически опрашивает эту ветку).

## Структура
- `tasks/inbox/` — новые задачи (одна за раз).
- `tasks/done/` — задачи, взятые и выполненные Build.
- `tasks/reports/<task-id>.md` — отчёты Build.
- `tasks/reports/read/` — прочитанные ботом отчёты (архив).
- `tasks/TEMPLATE.md` — шаблон задачи.

## Правила для Build
1. Берёт файлы из `tasks/inbox/` **только если в них есть frontmatter** (`id`, `created`, `priority`, `base`, `status`). Файл без frontmatter игнорируется.
2. Взяв задачу, ставит `status: taken` и пушит это изменение в `build-inbox`.
3. Работает в **отдельной рабочей ветке** `build/<task-id>`, созданной от коммита `base` из main.
4. Открывает **PR в main**. Никогда не пушит в main напрямую.
5. В `build-inbox` коммитит только: перенос задачи в `tasks/done/` и отчёт `tasks/reports/<task-id>.md`. Ничего больше.
6. Соблюдает разделы задачи «Не трогать» и «Разрешения».

## Содержимое отчёта
- Что сделано.
- Ветка (`build/<task-id>`) и ссылка на PR.
- Коммиты (sha + сообщение).
- Какие тесты запускались и их результаты.
- Что НЕ сделано и почему.
- Открытые вопросы.

## Ревью и слияние
- Бот-менеджер проверяет PR (не верит отчёту на слово, сверяет код и тесты).
- Обычные изменения бот вливает сам.
- Критичные изменения (контракты, деплой, адреса, ключи, NFT, крупные удаления) вливаются только после явного «да» владельца.
- Прочитанные отчёты бот переносит в `tasks/reports/read/`.

## Очередь
- В `tasks/inbox/` одновременно лежит одна задача.
- Задача с `priority: urgent` идёт вне очереди.
